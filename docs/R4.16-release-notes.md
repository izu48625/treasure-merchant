# R4.16 — ガチャの開封途中タスクキル復元と抽選結果保存の再監査

更新日：2026-10-24

## 結論
- ルーレットはR4.14で当選枠・財宝ID・品質を抽選開始時に封印保存。8.8秒の演出途中で再起動しても同じ結果に決着。
- スロットはR4.15で3リールと財宝ID・品質を開始時に封印保存。STOPは結果公開のみになり、再起動してもリール・賞品が変わらない。
- ガチャはR4.14/R4.15で最新バッチの各財宝ID・品質と入手回数を保存。ただし **開封途中の表示位置はセッション内のみ** だったため、R4.16で新たに保存・復帰する。
- 上記すべて IndexedDB での保存コミットを確認してから結果表示する仕組みを維持。結果を見たユーザーが次の操作へ進む前に保存完了を要求する。
- OS が IndexedDB のコミット前に完全終了した場合、その操作自体が成立しない場合がある。実機iOSでの不可抗力は残るため、絶対的な保存保証とは説明しない。

## R4.16で変更した箇所（index.html）
1. `state.gachaReveal` を追加。`{step,mode}` の形式で開封の表示位置（-1＝箱未開封、0〜N-1＝個別表示、N＝結果一覧）と次回の抽選モードを保存する。
2. 抽選時には既存 `state.lastGacha`（種類・回数・ID・品質・最大50個）と `gachaReveal` を同一セーブ更新で永続化する。保存完了前に結果画面を表示しない。
3. 「次を開ける」「まとめて表示」操作ごとに `gachaReveal.step` を保存し、保存コミットが完了してから表示を更新する。
4. 起動時は `state.gachaReveal` と `state.lastGacha` の両方が有効ならガチャタブ・結果モーダル・元のガチャ種類を復元する。個別表示の進行度と「同じN連をもう一度」も復帰する。
5. 開封画面を閉じる場合は `gachaReveal` をクリアして保存するが、`lastGacha` は維持する。通常の直近入手品リストは消えない。
6. JSONの取り込み時にも `gachaReveal` を検証・復元する。未対応の旧セーブでは `gachaReveal=null` として従来どおり起動できる。
7. 画面だけでなく裏側の保存値を試験。ガチャ排出率、市場、ルーレット・スロットの抽選確率や賭け金は変更していない。

## タスクキル模擬監査
- 途中の開封なし／4個目／一覧まで開封済み／ガチャ再抽選1回の各段階でセーブ・アプリ再起動を再現し、獲得品・品質・累計ガチャ・開封位置が維持されることを確認。
- ルーレットの財宝当選枠を固定して抽選し、当選ID・品質・投入G・二重付与防止がセーブ・再起動前後で同一と検証。
- スロット3つ一致でアイテム当選を再現し、3リール封印・1リール停止後の途中状態・残り一括停止・受取後の再起動を比較。旧slotVersion=2の途中セーブをslotVersion=3へ移行した後も何度再起動しても結果が一致することを確認。
- 保存完了を意図的に遅延する試験では、ガチャ抽選と開封ステップの結果が**コミット前に画面へ出ない**こと、コミット前に強制終了を模擬した場合には直前のセーブが復元され、コミット後は最新状態が復元されることを検証。
- 模擬ガチャ・遊技場再起動24チェック（ガチャ部）＋28チェック（遊技場部）、保存待機16チェックを確認。この数字は実装コードを擬似ブラウザ上で実行したものであり、実機実測値ではない。

## 制限・次の課題
- Webアプリの端末内保存では、ユーザーによるセーブ改変・時計改変や保存容量不足まで完全には防げない。
- iPhone Safari/PWAでの実際のOSタスクキル、IndexedDB容量上限、多タブ同時操作、OSアップデート後の復元は未実測。
- 保存領域やサイトデータを消去した場合の復元には、別途書き出したJSONバックアップが必要。
- OS終了前の未コミット操作を復元することはできない。通常プレイでは保存の確定後に結果を表示することでその可能性を減らす。
